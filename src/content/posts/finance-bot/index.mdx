This is the largest original build running on [my home server](/homelab/): a pipeline that imports bank transactions into a Firefly III ledger, categorises them, backs everything up nightly, and asks me about anything it isn't sure of over Telegram. 3,612 lines of Python across nine modules with roughly 970 more in tests, **stdlib only, no third-party dependencies at all**, source bind-mounted so a code change is a restart rather than a rebuild.

It publishes no ports. It long-polls an outbound API, so the Docker-bypasses-the-firewall problem simply cannot apply to it. It has no Docker socket either: the backup dumps over the network rather than running `docker exec`, specifically so a container that also invokes a language model is never handed root on the host daemon.

Most of what's interesting about it came from auditing the version before it, which had no backups, a scheduler that double-fired on restart, and a work queue that silently dropped items.

<Diagram title="The nightly chain">

- **04:30, Import.** SimpleFIN into the ledger. Cost is derived from the config, and spend is booked before the call.
- **05:00, Reconcile.** Match transfers the aggregator can't see. Dry-run by default; `--commit` to write.
- **05:15, Categorise.** Rules cover about 97%; one batched model call handles the tail above 0.85 confidence.
- **05:30, Back up.** Postgres, the bot's own state and the importer config, onto the file share.
- **1st monthly, Restore drill.** Restore the newest dump into a scratch database, compare row counts against live.

</Diagram>

## Backups That Are Proven, Not Assumed

The nightly dumps had been completing successfully for weeks. They were unrestorable.

The Postgres client major version must **match** the server, not merely exceed it. The base image shipped a v17 client against a v16 server, and a v17 `pg_dump` writes `SET transaction_timeout = 0;` into the dump header, a setting that doesn't exist before v17. The v16 server rejects the restore outright. Nothing surfaces at dump time, so the dumps look perfect right up until the moment you need one.

The fix was three parts: pin the client to v16, **assert the version at image build time** so a silent mismatch becomes a failed build, and add a monthly drill that restores the newest dump into a scratch database and compares row counts against live. It restores onto the existing server rather than a throwaway container, because that's the stricter test: it's the exact engine version a real restore would run on.

Retention is 30 dailies then 12 monthlies, written to the file share so the backups are one drag away from leaving the machine. An untested backup is a guess. The assertion and the drill are both cheap; finding this out during an actual restore is not.

## One Scheduler, With Memory

It's the only scheduler on the machine. No cron container, no host crontab, no systemd timer. Ten jobs, and three properties the version it replaced didn't have.

**Occurrences are persisted, not held in memory.** The predecessor kept a `fired` set in process memory and matched on `now.hour == 21`. Restarting the bot twice inside the 21:00 hour sent the daily digest three times. Now each job computes its most recent *scheduled occurrence* and runs only if that exact occurrence is unrecorded, so no number of restarts can re-fire anything.

**Missed work is caught up, not skipped.** Each job declares a grace window encoding whether running late is useful. A backup missed because the machine was down is worth running sixteen hours late; an evening digest arriving at lunchtime is noise, so its window is two hours and it's dropped. Encoding catch-up semantics per job rather than globally is the part worth stealing.

**A death mid-run is not the same as a failure.** A job whose process died partway through is recorded `interrupted` and becomes due again inside its window, because nothing completed. A job that ran and *failed* stays claimed and does not retry on the next tick, because the import spends real quota and a failing import that retries every minute would burn the entire day's budget before breakfast. Those two outcomes look identical in a naive scheduler, and they need opposite handling.

**Jobs run one at a time**, so the nightly chain can't interleave with itself.

The last line of that output is the quota ledger, which is the next problem.

- **Persisted occurrences.** No number of restarts can re-fire a job.
- **Per-job grace windows.** A missed backup catches up sixteen hours late; a missed digest is dropped.
- **Interrupted vs failed.** One is due again, the other stays claimed. Never the same thing.
- **One quota ledger.** A hard cap of 24 requests/day, counted once, in the unit the provider bills.
- **Undo log.** Every automated write records its previous value, so any of it reverses.
- **Tests.** Stdlib `unittest`, no fixtures, over the parts where being wrong is expensive.

## Counting What The Provider Actually Bills

The bank aggregator enforces a hard cap of 24 requests per day, and one import costs 8: a discovery call plus one per mapped account, so the cost is *derived from the config* rather than hardcoded. Add an eighth account and every run silently costs 9.

The previous design had two throttles that couldn't see each other: a CLI wrapper with an hourly stamp in `~/.cache`, and the bot with its own daily counter. Both counted *runs* rather than *requests*. Together they permitted well over 200 requests a day against a cap of 24. Two correct throttles that can't see each other are one broken throttle.

Now there's a single ledger, the CLI defers to it, and spend is booked **before** the call, so a failed run still burns its quota, which is what the provider actually charges. Three runs a day fit inside the cap: the nightly one plus exactly two manual pulls, and there's a flag that reports what's left without spending any of it.

Adjacent to that, the importer will happily execute *every* config file it finds in the import directory. A second config left behind after an experiment would silently double the quota spend every night, so the import job refuses to run unless there is exactly one.

## Rules First, A Model For The Tail

Declarative rules categorise about 97% of withdrawals. The remainder is merchants seen once or twice, which is exactly what a static rule list is bad at. The nightly pass sends that tail to a language model under three constraints:

- **One batched call per run**, never one per transaction.
- **Every returned category is validated against the live ledger category list.** The model does not get to invent a category.
- **Applied only above 0.85 confidence.** Anything below becomes a question in a Telegram queue instead of a silent write.

Then it learns: once a merchant resolves to the same category twice, it's folded into the *existing* rule for that category. Extending a small set of payee rules rather than creating one per merchant is what keeps the rule set legible. The system gets more deterministic the longer it runs, not less.

Every write records its previous value, so `/autolog` reviews recent automated changes and `/undo` reverses any of them. Automation that can write to a ledger needs an undo log; that isn't optional. And the model is referenced by alias rather than pinned version, precisely because it runs unattended at 05:15, where a rename would otherwise break it silently at a time nobody is watching.

## Learning A Rule That Actually Matches

The subtle part of folding a merchant into a rule is that the rule matches the ledger's *destination account name*, which is the raw payee string off the bank feed: `QT 992 OUTSIDE`, not `QuikTrip`. The same gas station appears under half a dozen of those.

So evidence is counted under one canonical merchant key, with every raw payee recorded against it as an alias. When a rule is written, the trigger is chosen from those aliases rather than assumed: an exact `is` match when the key is the payee, and a `contains` match only when the shortened key really is a substring of *every* payee it stands for. A `contains` trigger that was inferred from one alias and never checked against the rest is how a rule quietly starts eating transactions it was never meant to match.

## Talking To It In Plain English

The Telegram side started read-only and no longer is. When the queue posts a "needs your attention" list, the numbered items can be answered the way you'd answer a person: *"2 is my car insurance, 3 and 4 are food."*

The message goes to the model along with the open questions, the live category list and the last dozen turns of conversation, so pronouns and follow-ups resolve against what was just said. Whatever it infers comes back as a **proposal with Apply and Cancel buttons**. Nothing is written to the ledger until I tap. Proposals live in their own table and expire after 24 hours, so an ignored one can never be applied against a stale ledger a week later.

A category that doesn't exist yet is *offered* rather than rejected. Confirming it creates the category and a matching rule in the categorisation group, so the next transaction like it files itself without ever reaching a model. The nightly unattended pass still cannot invent a category. That guardrail is unchanged; only a human tap creates one.

The bug worth remembering here is a numbering one. Reply numbers wrap at 99 and only the last few batches stay resolvable, so the map from number to transaction has to agree with itself exactly. Renumbering only the unreachable items looks like the minimal fix and is the wrong one: it pushes an older batch past the retention limit and strands whatever was in it. Any renumbering has to re-batch the entire open set.

## Alerting On The Absence Of Success

The nightly import logs a dozen `There is already a transaction` errors and exits non-zero. Those errors *are* duplicate detection working correctly, because the import uses a rolling 7-day window and re-reads transactions already in the ledger every night.

Treating the exit code as truth would have alerted every night, and an alert that fires every night is an alert nobody reads. So errors are classified by content rather than exit code, and a heartbeat job treats *no successful import in 36 hours* as the alert instead.

## Testing The Parts Where Being Wrong Is Expensive

The test suite is 109 tests on stdlib `unittest`, with no fixtures and no test framework, matching the rest of the project. It runs in half a second, so there's no excuse not to. It doesn't chase coverage; it covers the four places where a subtle error is silent and costly: the scheduler's occurrence and grace-window arithmetic, the reply numbering and batch retention, backup pruning, and the guardrails on model output. Every one of those is a rule that only breaks in a state you won't reproduce by hand at 5am.

## What I Took From It

Every real bug in this system had the same shape: **something reported success while being wrong.** A dump that couldn't restore, a scheduler that forgot what it had done, two rate limiters that were each individually correct, a queue whose items entered a state with no path out, a learned rule matching more than it was taught. None of them threw an error.

Building the checks that catch that (a build-time assertion, a restore drill, a heartbeat, an undo log, a confirmation tap before any inferred write) is most of what separates automation you can leave running from automation you have to watch.
