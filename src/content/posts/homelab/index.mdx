**beast** is a machine I built and have never plugged a monitor into. It runs local GPU inference, a personal-finance pipeline, network file storage and seven Docker Compose stacks, and I administer all of it from a Mac mini and an iPhone, from anywhere.

It runs `multi-user.target` and has no display manager, because a headless box should never start one.

<Diagram variant="grid" title="The box">

- **CPU.** Ryzen 9 9900X, 12 cores / 24 threads, boost to 5.66 GHz, full AVX-512.
- **GPU.** RTX 5070 Ti, GB203 Blackwell, 16 GB VRAM.
- **Memory.** 59 GB usable, 8 GB swap.
- **Storage.** 2 TB Gen5 NVMe on LVM: 138 GB root, 1.7 TB data.
- **Network.** WiFi 7 uplink; the 5 GbE port sits unplugged.
- **OS.** Ubuntu 26.04 LTS, headless since the day it was built.

</Diagram>

## Nothing Is Exposed

Nothing is port-forwarded. There's no dynamic DNS and no exposed SSH. Every dashboard, the shell and the file share are reachable only over a WireGuard mesh (Tailscale) where each device is individually authenticated. `beast.local` resolves on the home LAN, and the firewall denies the dashboards on that path anyway.

<Diagram title="The only way in">

- **Phone or laptop.** Any enrolled device, on cellular or a café network.
- **WireGuard mesh.** Device authenticated individually; no port forwarding, no dynamic DNS, no exposed SSH.
- **One TLS front door.** A single proxy holds the mesh address and terminates HTTPS on a real certificate.
- **The service.** Shell, dashboards, file share, all bound to loopback behind that proxy.

</Diagram>

The non-obvious part, and the thing most home-lab writeups get wrong, is that **Docker publishes ports below the host firewall.** Docker writes published ports into the iptables `DOCKER` chain, which is evaluated *before* `ufw`'s `INPUT` rules. A container published as `"8080:8080"` is reachable from every host on the LAN, and `ufw deny 8080` does nothing about it. The firewall reports the rule. The port is open.

The first version of this machine answered that by binding every container explicitly, twice, never the wildcard:

```yaml
ports:
  # v1: Docker bypasses ufw, so bind loopback + the mesh address, never 0.0.0.0
  - "127.0.0.1:8080:8080"
  - "100.xx.yy.zz:8080:8080"
```

![The first iteration in the stack manager: every published port bound to loopback and to the mesh address, never the wildcard](images/dockge.png)

That worked, and it was still wrong in one way I didn't notice until I tried to use the machine from something other than a browser: every one of those services was plain HTTP.

![ss -lnt during the first iteration: every container port bound once to loopback and once to the mesh address, with SSH, Samba and Cockpit on the wildcard](images/ss-lnt.png)

`ss -lnt` is the command that settles arguments about any of this, and it's the first thing the operating guide tells you to run.

Host processes are a different category: `sshd`, `smbd` and Cockpit really are governed by `ufw`. Knowing which of the two you're dealing with is the difference between a firewall rule that works and one that only looks like it does.

## One TLS Front Door

The machine is now HTTPS-only, and the mesh address no longer belongs to Docker at all.

Every container publishes to `127.0.0.1` and nothing else. The mesh proxy (`tailscale serve`) is the only process holding the mesh address, and it terminates TLS on a real, publicly-trusted Let's Encrypt certificate issued for the machine's mesh hostname, renewed automatically. There is no self-signed certificate anywhere, no private CA to install on each device, and no browser warning to click through.

```yaml
ports:
  # v2: loopback only. The mesh address belongs to the TLS proxy, not Docker.
  - "127.0.0.1:8080:8080"
```

![tailscale serve status: eight public HTTPS ports on the mesh hostname, each proxying to a different loopback backend. The tailnet name is redacted](images/serve-status.png)

Each service gets its own HTTPS port on one hostname, so the whole box is a set of `https://` URLs that work identically from the laptop, the phone and a shell script:

| Service | URL | Backend on loopback |
|---|---|---|
| homepage | `:443` | `:80` |
| Open WebUI | `:3443` | `:3000` |
| Dockge | `:5443` | `:5001` |
| Firefly III | `:8443` | `:8080` |
| Importer | `:8444` | `:8081` |
| ComfyUI | `:8843` | `:8188` |
| Cockpit | `:9443` | `:9090` |
| Ollama API | `:11443` | `:11434` |

This is strictly better than the two-bind version it replaced. The number of processes holding a network-reachable address dropped from "every container" to one. Traffic on the mesh is encrypted end to end rather than merely tunnelled. And the certificate is real, which turned out to be the whole unlock for the next part.

![openssl s_client against the ledger port: verification OK, issuer Let's Encrypt, TLS 1.3, with the hostname redacted](images/tls.png)

Two things I got wrong on the way there:

- **A service's public port must never equal the port its container publishes.** Proxying `--https=8188` binds the mesh address on 8188, and Docker then cannot bind its own published 8188. The stack fails with `port is already allocated`, which reads like a Docker problem and is not one. That's why ComfyUI answers on `:8843`.
- **An app behind a proxy has to be told it's behind a proxy.** Three separate services needed it. Cockpit dropped the `Secure` flag on its session cookie until it was told to trust `X-Forwarded-Proto`, so login silently bounced with no error anywhere. It also rejects the login POST as cross-origin unless the *proxied* origin, port included, is in its allowed list. Firefly III renders correct absolute URLs only once it trusts the forwarded scheme, and its importer needs the public URL of Firefly rather than its own. All four settings name the public HTTPS port, never the loopback one.

## The Payoff: Real Apps, Not Just Browser Tabs

The reason a real certificate was worth the work: **native mobile apps now talk to the server directly.**

I run Abacus, an open-source native iOS client for Firefly III, pointed straight at my own ledger. Balances, spending, net worth and recent transactions are a home-screen tap, rendered by a real app instead of a pinch-zoomed admin panel. It's the same data the [finance pipeline](/finance-bot/) writes overnight, read from the machine in my apartment, from anywhere, over cellular.

<Diagram title="Phone to ledger">

- **The app.** Native iOS client, given a hostname and a personal access token.
- **The mesh.** Resolves the machine's hostname and routes to it; no port forward, no dynamic DNS, no VPN toggle to remember.
- **The front door.** TLS terminated on a genuine certificate, so the app's HTTPS stack accepts it with no exception to install.
- **The ledger.** Firefly III on loopback, publishing nothing, reachable only through the two hops above.

</Diagram>

Mobile apps are far stricter than browsers here. A browser lets you click past a self-signed certificate; an iOS app's networking stack simply fails, usually with an error that tells you nothing. Plain HTTP is refused outright by default. So "get a real certificate" isn't polish, it's the difference between a service being usable from a phone and not.

The pleasant surprise is that this needed no new inbound exposure at all. The ledger still publishes nothing, still binds loopback, and is still unreachable from the LAN. The app is simply on the mesh.

## Storage That Can't Wedge The OS

The Ubuntu installer leaves most of the volume group unallocated. A setup script carves the free extents into a separate 1.7 TB data volume rather than growing root, so a runaway download or a 14 GB model file can never fill the 138 GB OS disk. Docker's data root moves there too, since container images alone total over 80 GB.

![lsblk and df showing one NVMe split into a root volume at 76% full and a 1.7 TB data volume at 5%](images/storage.png)

Root sits at 76% full. That would be worth worrying about if it could grow, but nothing writes there by design, so it stays where it is.

The whole data volume is one Samba share tuned for Finder, so several workflows never need a shell: drop a model file in and the running service sees it immediately, and nightly backups land somewhere I can drag off the machine, because a backup that only exists on the machine it's backing up isn't a backup.

## What Runs On It

Seven Compose stacks, tracked in git and managed through a web UI.

<Diagram variant="grid" title="Seven stacks">

- **Ollama.** Local model serving. `OLLAMA_KEEP_ALIVE=5m` evicts the model from VRAM when idle, so the GPU stays free.
- **Open WebUI.** The chat front end for it, on its own HTTPS port.
- **ComfyUI.** Image and video generation, entire install persisted to a bind mount so the container stays disposable.
- **Firefly III + Postgres.** The finance ledger. The database publishes no ports at all.
- **finance-bot.** The automation pipeline around it. Long-polls outbound, so it publishes nothing either.
- **Cockpit + Dockge.** System admin and compose stack management, both mesh-only.
- **homepage.** A static landing page, so the bare mesh hostname is a dashboard of every link above.

</Diagram>

The largest original build on it is [the finance automation pipeline](/finance-bot/) wrapped around that ledger, which has a write-up of its own.

The provisioning is a set of idempotent shell scripts that each verify their own prerequisites. The Docker script refuses to run if the data volume isn't mounted or the driver isn't working, so a half-finished install fails loudly at the right step instead of producing something subtly broken three steps later.

## Things I Only Learned By Breaking Them

- **The GPU driver must be the `-open` variant.** This card is Blackwell; the legacy proprietary modules install fine and then fail to bind. The obvious "fix" for a driver problem is dropping the suffix, which is exactly wrong here.
- **Mount the directory, never the file.** A nightly job died with `exited 1` and completely empty stderr. A single-file bind mount pins to an inode, and the tool owning that credentials file refreshed its token by writing a temp file and renaming over it, an atomic replace that swaps the inode. The container was reading a file that no longer existed at that path. This applies to any single-file bind mount whose owner rewrites it atomically, which is most well-behaved software.
- **Validate downloads at the point of download.** A CDN handed out presigned URLs locked to a single byte range; parallel range requests raced into intermittent 403s, and the downloader wrote the 403 HTML page into the output file. The result was a 14 GB `.safetensors` that was really a web page, surfacing hours later as an inference crash with no obvious connection to its cause. The fix was one connection for that host plus a magic-byte check on the first 15 bytes.
- **One proxy is a single point of failure, so keep a second way in.** All eight web UIs are fronted by the same process. If its configuration were ever lost they would all go down together. Mesh SSH is independent of it and stays up, which is the difference between an outage and a drive home.

## Running It From A Phone

Anything longer than a minute runs inside `tmux`, so a dropped cellular connection doesn't kill it. `tmux new-session -A` attaches if the session exists and creates it if not, making reconnect and fresh start the same command. Long-running agent sessions run as a user systemd unit on their own tmux socket, specifically so restarting the unit can never take down my interactive SSH sessions.

The box ships with a written operating guide aimed at whoever runs it rather than whoever built it, plus an instruction file at its root encoding the rules (headless only, `sudo` needs a password, never publish a container on `0.0.0.0`) so that humans and agents working on it inherit the constraints instead of rediscovering them.
